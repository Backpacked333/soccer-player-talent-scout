# Intelligence engine contracts and ownership

## Status and ownership

These are integration contracts, not a claim of trained youth-model performance. `backend/app/intelligence/contracts.py` and its package exports are the authoritative Pydantic JSON interfaces. No new dependency is required. They coexist with the existing v1 API and preserve its private upload, worker, manual review and reporting contracts.

| Owner | Reserved implementation | Boundary |
| --- | --- | --- |
| Quantitative architect | `intelligence/contracts.py`, `intelligence/__init__.py`, shared `models.py`, `schemas.py`, `db.py`, `migrations.py`, contract/migration tests | Validation, limits, persistence schema; no model math |
| Spatial-action lane | `intelligence/action_value.py`, its tests and trainer CLI | Fit, score, progression and chronological evaluation |
| Opponent lane | `intelligence/ratings.py` and its tests | Explicit-duel extraction/deduplication, regularized fit, graph components, evaluation |
| Player-memory lane | `intelligence/identity.py`, `intelligence/memory.py` and their tests | Audited assignment service and deterministic current-corrected longitudinal history |
| Integrator | Routes, services, analytics adapters, UI/types, integration tests | Atomic snapshot reads, authorization, bounded calls, honest presentation |

Concrete callable interfaces are expressed as `ActionValueEngine`, `DuelRatingEngine`, and `PlayerMemoryEngine` Protocols. Implement a class satisfying the protocol or module-level functions `fit(snapshot, *, policy=None)`, `score(event, *, scope, artifact)`, `evaluate(snapshot, *, policy=None, test_fraction=0.25)` and `build(snapshot, *, player_id, as_of=None)` respectively. No engine imports another engine. Specialized non-model progression or matchup functions may live in the owning lane. Protocols do not supply fake implementations.

The shared immutable-in-meaning input is `EvidenceSnapshot(scope, matches, appearances, events, identities)`. Construction validates finite values, scope consistency, authorized roster membership and opposite-side opponent attribution. It does not replace authentication, foreign-key scoping, rights checks or database transaction isolation. Integrators construct it from authorized records, never deserialize a client-supplied snapshot as trusted data. Read all constituent tables in one coherent transaction; use repeatable-read for PostgreSQL or an explicit SQLite read transaction, not independent committed queries. Include canonical `Player.id`, not display name, jersey, anonymous tracker IDs or current profile role as cross-game identity.

### Additive event capture

Existing coordinates are retained but default to `coordinate_system='unknown'`. New optional fields:

- `coordinate_system`: `unknown`, `pitch_normalized`, or `attack_normalized`.
- `coordinate_provenance`: reviewed manual pitch mark or validated calibration/source reference. Image-space bounding boxes are never pitch coordinates or meters.
- `period` and `attacking_direction`: required for `pitch_normalized`; right-to-left becomes `(1-x,1-y)`. `attack_normalized` explicitly means the provider already normalized left-to-right and cannot also declare right-to-left. No invented period or body part is needed.
- `possession_retained`: explicit nullable boolean, never inferred from generic outcome or possession-like event names.
- `shot_outcome`: `goal` / `no_goal` only on an explicit shot. `outcome='successful'` on a shot does NOT mean goal. Ordinary eligible shots only; penalty/own-goal semantics must not be invented from missing labels.
- `contest_id`: reviewer-defined match-local physical duel identifier, only on `kind='duel'`. Duplicate inverse reports describe one contest, not two observations.
- Internal `identity_assignment_id` and `identity_assignment_revision`: persisted evidence provenance. Not accepted by the existing public `EventWrite`; an audited assignment service may attach them after authorization. `EventRead` exposes them. If the integrator later accepts linkage in requests, `validate_event` must check current scoped confirmed revision, actor and time range.

Unprovided fields remain null/unknown for old events, including synthetic seed records. An ordinary event edit may clear optional spatial semantics, never invent them. Legacy metrics continue working. Qualified coordinates alone do not make an action suitable for training, and no prior-only value is presented for missing observations.

## A. Spatial action value

Primary sources inspected: [socceraction xT documentation](https://socceraction.readthedocs.io/en/stable/documentation/valuing_actions/xT.html), [its source implementation](https://github.com/ML-KULeuven/socceraction/blob/master/socceraction/xthreat.py), [original xT exposition](https://karun.in/blog/expected-threat.html), and [VAEP documentation](https://socceraction.readthedocs.io/en/stable/documentation/valuing_actions/vaep.html).

xT is a spatial Markov model, not a positional lookup heuristic that may be renamed xG. Count all eligible move attempts and shots in the starting cell; goal reward is explicit goal count. Successful possession-retaining moves determine transitions. Failed moves terminate with zero continuation. Solve the disclosed regularized Bellman fixed point. A zero-reward terminal pseudo-count per cell is explicit regularization, not a youth-population prior. Default grid 8x6, at most 16x12; at most 10,000 training events and 2,000 iterations. Expose convergence and residual. Public scoring is `V(end)-V(start)` only on successful, explicitly possession-retaining pass/cross/carry with qualified start and end coordinates and sufficient observed support in BOTH cells. Do not silently value failures, shots, unsupported cells, draft actions or unseen cohorts. Internal zero states are not evidence that unseen locations have zero value.

`ActionValuePolicy` publishes provisional engineering sufficiency defaults: 3 training matches, 200 eligible actions, 20 shots, 3 goals, 5 actions per queried cell, terminal count 1, tolerance 1e-10. These are not empirically validated youth thresholds. Each training match requires a `StreamDeclaration`: explicitly complete eligible action stream, both sides including failed moves and non-goal shots, annotator/time/source, and separately rights-cleared model-training permission plus a rights reference. Ordinary footage processing rights do not authorize training. Selected highlights and unknown coverage must be rejected, not silently filtered until only successes remain. Any missing eligible-action semantics should make the training stream ineligible; disclose excluded streams.

`ActionValueArtifact` is versioned strict JSON (never pickle), bounded numeric arrays, explicit workspace/mode/season/age/role/competition scope, train match IDs, train fingerprint, policy, source rights references, coordinate convention, support counts and fit diagnostics. `validation_status='unvalidated_research'` cannot be changed to a marketing claim. A trainer/importer must cap input bytes before JSON decoding (suggested 8 MiB artifact, 32 MiB training snapshot); Pydantic list limits alone do not bound parsing allocation. Validate using `model_validate_json`; reject non-finite numbers, extra keys, incompatible versions, malformed shapes, missing rights, inconsistent counts and leaked train/test IDs. Never auto-load arbitrary user filesystem paths in a request. No validated weights ship with the app; score without an appropriate fitted artifact is null with reasons.

Prefer socceraction when actual SPADL semantics and its dependency stack are available. The current app lacks SPADL period/bodypart/result semantics, so do not forge those fields to satisfy a dependency. An explicitly named narrow implementation of the Markov equations using existing dependencies is acceptable with mathematical oracle tests and a clear deviation disclosure (regularization, grid orientation, eligible action set). No library code is copied by the contract layer. VAEP remains unavailable: it needs score/concede-next-10-action labels, last-three-action/game context and calibrated trained classifiers, not this spatial model.

A separate observed progression report may show normalized pitch-length displacement on supported reviewed moves, eligible/total action denominator, normalization provenance and limitations. It is not meters, xT, a calibrated impact estimate or a talent score.

Evaluation must say exactly which valid binary target it evaluates. If only local shot conversion is evaluated, label it as shot-cell calibration, not calibrated long-horizon possession value; possession-ending goal labels cannot be inferred from incomplete streams. Compare with a train-only constant baseline. Brier/log loss require valid binary labels and grouped chronological match holdouts. Synthetic oracle tests are not empirical model validation.

## B. Opponent-adjusted direct duels

Primary reference inspected: [OpenSkill manual](https://openskill.me/en/stable/manual.html). Team outcomes can update an explicit competitive model but match wins do not establish each child's ability. The chosen narrow model is regularized binary Bradley–Terry for explicit reviewed direct duels, not automatic OpenSkill updates from match score.

Accept only approved `kind='duel'` events with known binary outcome, reviewer provenance, distinct opposite-side authorized roster actors and currently valid identity linkage if present. `successful` means this actor won that explicitly reviewed duel. No draws supported in v1. Do not reinterpret tackles, generic headers, team wins, passes or unopposed recoveries as duels.

Count one physical contest once. Preferred key `(match_id, contest_id)`; legacy events without one may use exact `(match_id, timestamp_seconds, sorted(actor, opponent))`. Resolve consistent mirrored rows to one deterministic representative; if a contest group disagrees about winner/actors/time, exclude the ambiguous contest and report evidence IDs. Avoid fuzzy time windows that collapse distinct contests or silently double-count uncertain ones. Explicit IDs alone must not bypass exact inverse-duplicate detection. Keep source IDs for drilldown. Inconsistent contests remain unresolved.

Within the requested `CohortScope`, fit `P(i wins j)=sigmoid(theta_i-theta_j)` with independent zero-centered Gaussian prior SD 1.5 by default. Fit deterministically with convergence diagnostics and proper separation-safe regularization. Laplace/Hessian uncertainty is explicitly an approximation conditional on independent contests; it is NOT calibrated match-clustered confidence. Do not hide approximate intervals behind generic confidence labels.

Build observed graph connected components and expose stable component IDs. No cross-component universal order, no rank for unseen players, no arbitrary 0–100 mapping. A role-specific fit admits only events with BOTH actors of that historical appearance role; `all_roles` is an explicit mixed-role scope, not a role-adjusted fit. Never compare role-specific and mixed-role fits as interchangeable. Default ranking support: 20 contests, 3 matches, 3 distinct opponents, max one-match share 0.6; thresholds are provisional. Unknown roles do not establish a defensible role comparison. Null for no observations even though the mathematical prior exists.

Hard maxima in `DuelRatingPolicy`: 128 players, 10,000 contests and 200 iterations. Check caps BEFORE allocating matrices/factoring; refuse oversized work rather than silently sample. Do not run unbounded dense cubic fitting on a request. A sparse/iterative solution is preferable, with bounded uncertainty calculation. Parent/integrator should cache only by complete evidence fingerprint if needed, or run bounded fits off the interactive thread. Hyperparameters must not be tuned on held-out matches.

Evaluate on whole later matches, never random contest rows; train-only baseline, Brier/log loss and coverage of held-out actors/edges. Unseen actors and train-disconnected pairs are unscorable, not 50% filler predictions. Report those exclusions. Do not call held-out performance empirically verified until real authorized data has actually been evaluated.

## C. Canonical identity and longitudinal knowledge

`Player.id` is the durable canonical identity already present. `Appearance` captures a player's match-specific side, jersey, role and declared exposure; `Match.age_group` supplies the historical age cohort. Current profile edits never rewrite those historical labels. A player changing shirt number across games is the same canonical identity only by authorized reviewer linkage, not by similarity, face recognition or autonomous cross-video tracking.

`TrackIdentityAssignment` stores current `proposed/confirmed/rejected` decision over `(upload_id, track_id, start_seconds, end_seconds)` with target canonical `player_id`, source, confidence (proposal metadata only), reason, created/reviewed actor/time and revision. It intentionally references `Player`, not `Appearance`: existing roster replacement deletes/recreates appearance IDs. Audit EVERY proposal, confirmation, rejection and reassignment using the existing `AuditLog` before/after/reason in the same transaction. Require a reason and `expected_revision` for corrections. SQLAlchemy versioning protects stale updates; a match-level lock or SQLite immediate write transaction is additionally required to prevent concurrent overlapping inserts. Version checks alone do not serialize range conflicts.

Identity service requirements:

1. Load workspace/mode/match/upload/track/roster/canonical player through scoped joins. Confirm actual player/goalkeeper observations in the declared interval and valid authorized roster/rights. Never use raw `TrackObservation.player_id` as cross-match identity or evidence approval.
2. Closed intervals are used; touching endpoints conflict conservatively. Overlapping confirmed assignments on the SAME track cannot identify different players; overlapping DIFFERENT tracks cannot identify the SAME player. Reject duplicate or conflicting confirmations with inspectable reasons. Multiple ambiguous proposed candidates may coexist, but remain unresolved until audited confirmation. Exclude ball/referee observations.
3. Confirmation never approves events. Explicit reviewed event creation/reattribution is a separate act. Link reviewed evidence to the confirmed assignment revision if it depends on that track.
4. Before rejecting/reassigning a confirmed identity, invalidate/demote all dependent events to draft and audit their old/new states in the same transaction, or require the reviewer to explicitly correct those events first. Never transfer approved event statistics to a different player just because a track target changes. Engines additionally reject stale/missing/nonconfirmed assignment revisions. A manually re-reviewed event can clear linkage in an explicitly audited correction.
5. Roster changes must reject conflicting retained assignments or invalidate them and dependent events atomically. Match deletion cascades assignments; privacy deletion must not preserve identifying audit snapshots. Retain no biometric embeddings.

`PlayerKnowledge` is deterministic recomputation from approved events, scoped roster appearances and current confirmed revisions, not an appended LLM prose memory or detector training. `PlayerMemoryEngine.build(snapshot, player_id=..., as_of=...)` returns chronological `LongitudinalPoint`s with cumulative evidence/exposure, denominator-aware rates, historical appearance role/age, evidence IDs, relationship evidence and a version/fingerprint. Later reviewed matches change the cumulative history; deleting/rejecting/reattributing an event repairs past and later cumulative values on the next recomputation. Include the policy/method, scope, cutoff, canonical IDs, dates, roster/side/role/coverage, review state, events and identity revisions in the fingerprint. Sort unordered input collections by stable IDs first. Fingerprints are correction detection, not cryptographic authenticity or anonymization.

Only relationship names permitted: `co_rostered_teammate`, `co_rostered_opponent`, `direct_duel`. Shared match membership is NOT on-pitch overlap, chemistry, friendship or a predictive interaction score. Co-roster relations cite match IDs; direct duels cite deduplicated approved physical contests/event IDs. Reciprocal results may be derived once from a physical duel but must not become two contests. Cap input and output size; do not build an unbounded all-pairs workspace graph when rendering one profile.

As-of histories include only matches on/before the cutoff; same-date matches must not leak future-date knowledge. This is a current-corrected reconstruction of historical performance, NOT a bitemporal reconstruction of what the system knew at that old wall-clock time. Cohort-specific histories must not silently pool season/age/role/competition. Declared exposure and selected-review bias remain visible. `predictive_model_status='not_trained_or_validated'` distinguishes accumulated reviewed knowledge from unvalidated predictive ML.

## Shared evaluation and fingerprint helpers

- `chronological_match_split(matches, test_fraction=0.25)` returns deterministic `(train_ids, test_ids)` tuples, groups WHOLE dates and matches, rejects fewer than two dates/duplicate IDs/invalid fraction/over 1,000 matches. Same-date matches stay on one side because intraday order is unknown.
- `canonical_fingerprint(value)` hashes finite canonical JSON with stable dictionary order; callers sort unordered lists by stable IDs. No NaN or pickle.
- `EvaluationReport` prevents overlap, empty evaluated sets, nonchronological boundaries, unavailable numeric performance and missing baseline Brier scores. This validation cannot prove reported metrics were actually computed: engine tests must.
- `utc_timestamp` makes explicit database timestamps UTC, including SQLite's naive datetime representation.

## Schema migration and integrator checklist

Schema v2 adds event semantics and `track_identity_assignments`, plus `schema_migrations` as a database-level checksum ledger. No evidence is seeded, reset, inferred or auto-approved. The additive migration must preserve existing v1 rows exactly and leave unknown semantics unknown. It runs transactionally, with SQLite `BEGIN IMMEDIATE` / PostgreSQL schema-version row locking, checks old layout and advances the version only after all DDL and its ledger record succeed. Unsupported versions fail closed. Operators should back up persisted databases before upgrades; no downgrade/reset shortcut is provided.

The identity lane owns service behavior, not the migration. The integrator must expose assignment operations and event linkage only after the above checks exist; must update roster corrections to handle assignment dependencies; and must keep every new endpoint private, CSRF protected and workspace/mode scoped. The architect's new public event fields fit existing `model_dump()` persistence and audit paths without route edits. Existing endpoints can capture explicit semantics immediately but this alone does NOT activate trained scoring.

Required tests per lane: toy/oracle probabilities, deterministic/permutation invariance, coordinate rotation, missingness, rights/highlight gates, finite bounds, held-out leakage and train-only baselines, all-win regularization, disconnected graphs, inverse/conflicting duplicate contests, cross-tenant/mode/role/season refusal, chronological evidence accumulation, correction/deletion repairs, assignment overlap and concurrent stale revision behavior. Real-vs-synthetic status must remain explicit in every report. No browser test, model download or deployment is part of this contract work.

## Full-match processing handoff: 90 minutes plus stoppage

The user requires the whole authorized source, not the first frame-budget-sized prefix. `app.processing_contracts` owns `FullMatchPolicy`, `ChunkInterval`, `FullMatchPlan`, `ProcessingCoverage`, `ProcessingChunkRead`, and `chunk_scoped_track_id`. `app.schemas` owns `ChunkRequest`, `ChunkResult`, `ProcessingChunkPage`, `ObservationRead`, and `ObservationPage`. Worker/vision/fullmatch implementation belongs to the parent lane; these contracts do not by themselves execute a full scan.

- Plan against the **probed source duration**, including stoppage and extra time, not the nominal 5,400-second match field. Default duration ceiling remains 10,800 seconds (configurable to 14,400). `FullMatchPlan` validates an ordered gap-free half-open partition `[0, source_duration)`, bounded to 1,440 chunks. Default chunks are 120 seconds at a disclosed 0.5-second sampling interval, not continuous frame analysis. A 96-minute source has 48 default chunks. The final chunk may be shorter.
- Defaults: `Settings.processing_chunk_seconds=120`, `processing_sample_interval_seconds=0.5`, `processing_max_chunks=1440`, `processing_observation_batch_size=500`, `processing_max_chunk_attempts=3`. Combine these with the actual vision adapter's frame/observation limits to construct `FullMatchPolicy`. `FullMatchPolicy` rejects a cadence that cannot fit its per-chunk frame budget. Upload cap defaults to 8 GiB and accepts at most 16 GiB; the existing streamed upload and ranged private-media I/O must remain streamed. Operators must size private disk/quota/proxy/timeouts accordingly; larger limits are not a guarantee for every bitrate.
- Persist `ProcessingChunk` IDs and immutable geometry **before** processing. Unique `(job_id, sequence)` prevents duplicate segments. `plan_fingerprint` must cover source SHA, all chunk boundaries, sampling policy, model version/checkpoint digest and inference settings; changing these requires an explicit new processing job, not mutating a completed plan. Persist the same fingerprint and cadence in every chunk. No raw videos or credentials enter fingerprints.
- `ChunkRequest` contains `chunk_id`, `sequence`, `start_seconds`, `end_seconds`, `source_duration_seconds`, `sample_interval_seconds`, `max_sampled_frames`, `max_observations`, and `plan_fingerprint`. Worker calls a bounded adapter for this interval, never loads the full video into RAM, and consumes absolute source timestamps. Seek/decode must filter preroll and keep `[start,end)` ownership; timestamps must not restart at zero per chunk. Frame/observation caps and timeout are **failure/incomplete coverage**, never successful prefix completion. Late source frames and stoppage must be demonstrably visited by worker tests.
- `ChunkResult` is one bounded chunk: ID/sequence/interval, `status=completed|failed`, absolute `processed_through_seconds`, decoded/sample counts, model version, bounded observations, optional error code, message, bounded warnings. Successful results require detector evidence through the interval end and at least one sampled frame; zero detections is valid, fabricated detections are not. Worker must additionally match the result to its request, enforce the request's tighter counts, source/config fingerprint, tenant/mode/upload and current authorization. `result_fingerprint` hashes the accepted bounded result; observations are committed in bounded DB batches. No candidate or approved events are implied.
- Claim only pending/failed/expired unfinished chunks. Each claim rotates a persisted random `lease_token`, increments `attempts` and ORM `revision`, and sets worker/expiry. Renew before expiry. Every progress/final write must compare the chunk token/revision **and** current parent-job lease in one transaction; stale workers discard results. SQLAlchemy optimistic versioning is present, but bulk SQL must explicitly include the fence predicates. Commit observations plus `completed` status/result fingerprint atomically. An interrupted transaction must be safely replayable; completed chunks are skipped idempotently. Failed/incomplete chunks must not advertise full coverage.
- A retry must NEVER execute the old whole-upload observation deletion. It must not delete completed chunks, their observations or any confirmed identity. A fresh explicit job has fresh chunk IDs; reviewed old evidence is retained until an audited correction/deletion policy is applied. Automatic retry is not a reviewed reattribution.
- Both `TrackObservation.track_id` and `TrackIdentityAssignment.track_id` use `chunk:<canonical chunk UUID>:<local tracker ID>` (local ID 1–37 ASCII letters/digits/`_.-`; total at most 80). `chunk_scoped_track_id` produces it. Different chunks/reruns cannot imply the same player from equal tracker-local numbers. Legacy track strings are preserved unchanged. `TrackObservation.processing_chunk_id` records nullable FK provenance; identity services require the matching observation and source interval. Scene cuts within a chunk must reset the local tracker with a distinct local epoch (e.g. `cut2.17`) or shorten/split the plan; chunk scoping alone does not solve camera-cut identity.
- `JobRead.processing_coverage` is an optional small summary; never attach full-match observation arrays. Integrator exposes private cursor-paginated observations (at most 500/page) and chunks (100/page), not unbounded scans. `ProcessingCoverage.status=complete` requires every planned chunk and the complete source interval at the disclosed cadence. It always declares `reviewed_event_coverage=not_established_by_detection`. Metadata-only processing produces **zero detection coverage**, remains honest about missing weights/capabilities, and never upgrades `StreamDeclaration` to a complete reviewed training stream.

Schema **v3** adds `processing_chunks`, nullable observation chunk provenance, and its paging index. `init_db` applies additive v1→v2→v3 migrations, each atomically ledgered/serialized; an interruption after v2 can resume to v3. Existing v2 identity decisions, events, jobs, raw timestamps and track IDs remain unchanged, and no historical chunk completion is invented. Fresh databases bootstrap v3. PostgreSQL migration paths require a live integration run before production claims; SQLite preservation/rollback/concurrency tests are included. Full-match worker resume/fence/late-frame/metadata-only tests remain the parent's implementation responsibility.
